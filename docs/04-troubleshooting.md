# 04. 트러블슈팅: 문제, 원인, 해결, 결과

> **요약** 실서비스 배포에서 겪은 문제 7가지. 프롬프트 비대화(응답 6.8초에서 1.5초로), 로컬에서는 잡을 수 없는 토큰 만료 버그(403과 401), 예외를 중복으로 오역한 거짓 메시지, 휘발성 디스크, 무료 API의 간헐 혼잡, 예고 없이 바뀌는 외부 API 응답, 조용히 실패하는 CSS 마이그레이션. 제목만 훑고 궁금한 것만 펼쳐 봐도 된다.

실서비스 배포 과정에서 실제로 겪은 문제들이다. 각 사례는 현상, 원인 분석, 해결, 결과 순서로 기록했다.

---

## 사례 1. 프롬프트 비대화로 채팅 응답 6.8초

<details markdown="1">
<summary><b>현상, 원인, 해결, 배운 것 (펼쳐 보기)</b></summary>

현상: 대화 품질 개선 작업(리듬 규칙, Big5 연동, 친밀도 반영)을 거듭할수록 응답이 느려져 6.8~9.0초에 달했다. 특정 이모티콘(ㅠㅠ)을 과도하게 반복하는 품질 문제도 같이 나타났다.

원인 분석: 응답 시간을 3회 실측하고 서버 로그에서 시스템 인스트럭션 길이를 확인하니 14,043자였다. 기능을 더할 때마다 프롬프트 파일에 규칙과 예시가 누적된 것이 원인이었다. 예시 문장의 대부분이 "ㅠㅠ"로 끝나서 모델이 그 패턴을 따라 한 것도 같은 뿌리였다.

해결: 프롬프트 3개 파일을 "규칙은 전부 보존, 중복과 예시만 제거" 원칙으로 재작성했다 (26.2KB에서 7.0KB로). 동적 컨텍스트와 중복되던 시간대별 톤 가이드를 삭제하고, 예시 10개를 핵심 1~2개로 줄였다. 동시에 이모티콘 사용 규칙(연속 턴 금지, 3턴에 1회 수준)을 명시했다.

결과: 인스트럭션 14,043자가 3,666자로, 응답 6.8~9.0초가 1.5~2.0초로 줄었다. 같은 시나리오 5턴 테스트에서 ㅠㅠ는 0회(기존에는 거의 매 턴), 대화 리듬 규칙은 전부 유지됨을 확인했다.

배운 것: 프롬프트는 코드처럼 기술 부채가 쌓인다. 추가만 하고 리팩터링하지 않으면 토큰 비용, 지연, 품질이 동시에 나빠진다. 길이를 로그로 상시 노출해 둔 것이 진단을 빠르게 했다.

</details>

## 사례 2. 24시간 뒤 세션이 조용히 죽는 버그: 403과 401의 시맨틱

<details markdown="1">
<summary><b>현상, 원인, 해결, 배운 것 (펼쳐 보기)</b></summary>

현상: 배포 다음 날부터 "미안해, 지금 답변을 할 수 없어"(채팅 실패)와 설정 로드 실패가 발생했다. 서버 로그에는 `Expired JWT token`이 초당 수 회 반복됐다.

원인 분석: 액세스 토큰(24h) 만료 자체는 정상이다. 문제는 프론트의 "401 수신 시 refresh 토큰으로 재발급" 인터셉터가 한 번도 발동하지 않은 것이었다. 백엔드를 확인하니 Spring Security에 `authenticationEntryPoint`가 없어 미인증 요청이 기본값인 403으로 떨어지고 있었다. 프론트는 401만 기다리고 백엔드는 403만 주니 재발급 루프가 영원히 시작되지 않았다.

해결: Security 설정에 커스텀 EntryPoint를 추가해 미인증과 만료를 401과 JSON 에러 바디로 통일했다. 403은 인증은 됐지만 권한이 없는 경우(소유권 위반)에만 쓰도록 시맨틱을 분리했다.

결과: 만료 시 첫 401에서 자동 재발급 후 원 요청을 재시도한다. 사용자는 아무것도 느끼지 못한다. 리프레시(7일)까지 만료되면 로그인 화면으로 자연스럽게 유도된다.

배운 것: 이 버그는 로컬 테스트로는 잡을 수 없다. 토큰이 만료되려면 24시간이 필요하다. "배포 후 하루 지난 시점"도 테스트 시나리오라는 것, 그리고 HTTP 상태 코드의 시맨틱(401과 403)은 사소해 보여도 클라이언트 자동화 로직의 계약이라는 것을 배웠다.

</details>

## 사례 3. "일기가 이미 있어요": 사실은 컬럼 길이 초과였다

<details markdown="1">
<summary><b>현상, 원인, 해결, 배운 것 (펼쳐 보기)</b></summary>

현상: 배포 환경에서 일기 생성 시 "오늘의 일기는 이미 만들어졌어요"가 떴지만, 실제로 일기는 존재하지 않았다.

원인 분석: 서버 로그를 추적하니 일기와 그림 생성은 전부 성공했고, 마지막 저장에서 `SQL Error 22001: value too long for varchar(500)`이 났다. 두 가지가 겹친 복합 버그였다.

1. 무료 배포 환경에서 삽화를 Pollinations URL로 저장하도록 바꿨는데, URL에 그림 프롬프트 전체가 인코딩되어 들어가 500자 제한을 초과했다. 로컬에서는 짧은 파일 경로라 재현되지 않았다.
2. 저장 코드가 `DataIntegrityViolationException`을 전부 중복 일기로 번역했다. 길이 초과가 "이미 존재함"으로 둔갑했다.

해결: `image` 컬럼을 500자에서 1500자로 확장했다 (엔티티, init-db.sql, 운영 DB ALTER 동시 반영). 예외 번역도 고쳤다. 무결성 위반 시 실제로 일기가 존재하는지 재조회해서 중복일 때만 중복 응답을 주고, 아니면 원 예외를 로깅한 뒤 전파한다.

배운 것: catch 절에서 예외를 "가장 흔한 원인"으로 뭉뚱그려 번역하면, 드문 원인이 발생했을 때 오진단을 유발하는 거짓 메시지가 된다. 예외 번역은 반드시 사실 확인을 거쳐야 한다.

</details>

## 사례 4. 재시작하면 사라지는 그림: 휘발성 디스크

<details markdown="1">
<summary><b>현상, 원인, 해결, 배운 것 (펼쳐 보기)</b></summary>

현상: Render 무료 인스턴스는 재시작과 재배포마다 디스크가 초기화된다. 삽화를 로컬 파일(`/images/{uuid}.png`)로 저장하는 기존 설계로는 일기 그림이 하루를 못 넘기고 깨질 수밖에 없었다.

원인 분석: 배포 전 리서치 단계에서 무료 티어의 "ephemeral filesystem" 제약을 확인하고 미리 대응했다. 대안은 셋이었다. 유료 오브젝트 스토리지(비용 발생), 외부 스토리지 무료 티어(계정과 연동 추가), 그리고 Pollinations는 URL 자체가 이미지(프롬프트 결정적)라는 성질을 활용하는 방법.

해결: 세 번째를 택했다. 이미지 생성 성공 시 바이트 대신 원본 URL을 DB에 저장하는 `prefer-remote-url` 모드를 추가하고 무료 배포 프로필에서만 활성화했다. 로컬과 VM 배포는 기존 파일 저장을 유지한다(환경별 플래그). 프론트는 상대 경로와 절대 URL을 모두 처리하도록 단일 변환 함수를 보강했다.

결과: 재배포와 재시작 후에도 모든 일기 삽화가 유지된다. 인프라를 바꾸는 대신 저장 전략을 환경에 맞춘 사례다.

</details>

## 사례 5. 무료 이미지 API의 간헐 혼잡: 복구 경로 설계

<details markdown="1">
<summary><b>현상, 원인, 해결, 배운 것 (펼쳐 보기)</b></summary>

현상: Pollinations(무료 공용 인프라)가 혼잡 시간대에 500과 402를 간헐적으로 반환했다. 그림 없는 일기가 생겼고, 당시 UX에는 재시도 수단이 없었다. 감정 선택은 하루 1회라 생성 버튼도 다시 누를 수 없었다.

해결: 세 겹으로 대응했다.

1. 재시도 강화: 지수 백오프 재시도를 1회에서 4회로 (혼잡은 보통 수초 내 해소된다)
2. 복구 API: `POST /api/diary/{id}/image`. 일기 본문은 유지하고 삽화만 재생성한다
3. 복구 UX: 그림 없는 일기 상세에 "다시 그려달라고 하기" 버튼, 감정 선택 후 실패 시 안내 모달 재진입 경로

배운 것: 무료 인프라 전제에서는 "실패하지 않게"보다 "실패해도 사용자가 복구할 수 있게"가 현실적인 설계 목표다. 모든 실패 지점마다 "이 상태에서 사용자가 할 수 있는 다음 행동이 있는가"를 점검하게 됐다.

</details>

## 사례 6. 카카오 신규 콘솔과 kakao_account null: 외부 API 응답은 계약이 아니다

<details markdown="1">
<summary><b>현상, 원인, 해결, 배운 것 (펼쳐 보기)</b></summary>

현상: 카카오 로그인에서 토큰 교환까지 성공했는데 최종 단계에서 500이 났다. 로그: `Cannot invoke "Map.get" because "kakaoAccount" is null`.

원인 분석: 2025년 말 카카오 개발자 콘솔 개편 이후 신규 앱은 동의항목 설정 구조가 바뀌어, 동의항목이 없는 앱의 `/v2/user/me` 응답에 `kakao_account` 블록 자체가 빠질 수 있다. 기존 코드는 이 블록의 존재를 전제로 체이닝 접근하고 있었다.

해결: null-safe 파싱과 폴백 체인을 넣었다. 닉네임은 `kakao_account.profile`, `properties`, 기본값("집사") 순으로 찾고, 이메일이 없으면 카카오 ID 기반의 결정적 대체 이메일(`kakao_{id}@catus.local`)로 유니크 제약을 충족한다. 닉네임은 어차피 온보딩에서 직접 입력받으므로 UX 손실은 없다.

추가로 잡은 것: 토큰 교환의 `redirect_uri`가 설정 파일의 미해석 템플릿 문자열(`{baseUrl}/...`)로 전송되던 잠복 버그. 인가 요청과 토큰 교환의 redirect_uri는 문자열까지 일치해야 한다(KOE303). 환경변수로 외부화해 프론트 주소와 단일 소스로 맞췄다.

배운 것: 외부 API 응답 구조는 문서가 아니라 그 시점의 스냅샷이다. 선택적 필드는 전부 없을 수 있다고 가정하고 파싱해야 하며, OAuth 파라미터는 등록값, 인가 요청, 토큰 교환 세 곳의 완전 일치가 계약이다.

</details>

## 사례 7. (프론트) Tailwind v4 마이그레이션: 입력창이 화면을 뚫는 이유

<details markdown="1">
<summary><b>현상, 원인, 해결, 배운 것 (펼쳐 보기)</b></summary>

현상: 모바일에서 채팅 입력 바가 오른쪽으로 16px 돌출했다. 수치로는 좌측 여백 39px, 우측 7px로 비대칭이었다.

원인 분석: Tailwind v4는 진입 구문이 `@import "tailwindcss"`로 바뀌었는데, 구버전 문법(`@tailwind base`)을 쓰면 에러 없이 조용히 무시된다. preflight(box-sizing: border-box 리셋)가 전역에서 빠지면서 `width: 100% + padding`이 content-box 기준으로 계산돼 넘친 것이다. 같은 뿌리에서 h1 거대화, 겹침 등 증상이 연쇄됐다.

해결: 진입 구문을 교체하고 Vite 템플릿의 잔여 CSS를 제거했다. 이후 뷰포트 390x844 헤드리스 스크린샷으로 좌우 여백 39/39px 대칭을 수치로 검증했다.

배운 것: 조용한 실패가 가장 비싸다. 메이저 버전 마이그레이션에서는 동작하는 것처럼 보여도 기반 레이어(리셋 CSS)부터 눈이 아닌 수치로 검증해야 한다.

</details>
