# 운영과 회고

배포 뒤 실제로 겪은 문제 넷입니다.

## 사례 1. 프롬프트가 불어나 응답이 7초

대화 품질을 손볼수록 답장이 느려졌습니다. 리듬 규칙, Big5 연동, 친밀도 반영을 차례로 넣고 나니 응답이 6.8초에서 9초 사이였고, 달이가 "ㅠㅠ"를 거의 매 턴 붙이는 버릇도 같이 생겼습니다.

응답 시간을 세 번 재고 서버 로그에서 시스템 인스트럭션 길이를 보니 14,043자였습니다. 기능을 더할 때마다 프롬프트 파일에 규칙과 예시가 쌓인 것이 원인이었습니다. 예시 문장 대부분이 "ㅠㅠ"로 끝나서 모델이 그 패턴을 따라 한 것도 같은 뿌리였습니다.

프롬프트 파일 셋을 "규칙은 전부 남기고 중복과 예시만 뺀다"는 원칙으로 다시 썼습니다. 동적 컨텍스트와 겹치던 시간대별 톤 가이드를 지우고, 예시 열 개를 한두 개로 줄였습니다. 이모티콘 규칙(연속 턴 금지, 3턴에 1회 수준)은 이때 명시했습니다.

인스트럭션은 14,043자에서 3,666자로, 응답은 1.5초에서 2초 사이로 내려왔습니다. 같은 5턴 시나리오를 전후로 돌려 "ㅠㅠ"가 사라지고 리듬 규칙은 모두 살아 있는 것을 확인했습니다.

## 사례 2. 토큰 만료 후 재발급이 돌지 않음

배포 다음 날부터 채팅이 "미안해, 지금 답변을 할 수 없어"로 실패하고 설정도 열리지 않았습니다. 서버 로그에는 `Expired JWT token`이 초당 몇 번씩 찍혔습니다.

액세스 토큰(24시간) 만료 자체는 정상입니다. 문제는 프론트의 "401을 받으면 refresh 토큰으로 재발급" 인터셉터가 한 번도 돌지 않은 것이었습니다. Spring Security에 `authenticationEntryPoint`를 두지 않아 미인증 요청이 기본값인 403으로 떨어지고 있었습니다. 프론트는 401만 기다리고 서버는 403만 주니 재발급이 시작될 수 없었습니다.

EntryPoint를 추가해 미인증과 만료를 401과 JSON 에러 바디로 통일하고, 403은 인증은 됐지만 권한이 없는 경우에만 쓰도록 나눴습니다. 지금은 첫 401에서 재발급한 뒤 원 요청을 다시 보내고, 리프레시(7일)까지 만료되면 로그인 화면으로 보냅니다.

## 사례 3. 없는 일기를 중복이라고 답함

배포 환경에서 일기를 만들면 "오늘의 일기는 이미 만들어졌어요"가 떴는데, 실제로 일기는 없었습니다.

로그를 따라가 보니 일기와 그림 생성은 모두 성공했고, 마지막 저장에서 `SQL Error 22001: value too long for varchar(500)`이 나 있었습니다. 무료 배포 환경에서 삽화를 Pollinations URL로 저장하도록 바꿨는데, URL에 그림 프롬프트 전체가 인코딩돼 들어가 500자를 넘긴 것입니다. 로컬은 짧은 파일 경로라 재현되지 않았습니다.

그런데 길이 초과가 왜 "이미 있음"으로 보였는가가 진짜 문제였습니다. 저장 코드가 `DataIntegrityViolationException`을 전부 중복 일기로 번역하고 있었습니다. 대부분은 맞는 번역이지만 길이 초과처럼 드문 경우에 틀립니다.

컬럼은 1500자로 늘렸습니다. 예외 번역은 무결성 위반이 나면 실제로 일기가 있는지 다시 조회해서 중복일 때만 중복 응답을 주고, 아니면 원래 예외를 로깅하고 전파하도록 고쳤습니다.

## 사례 4. 그림 생성 실패와 복구 경로

Pollinations는 무료 공용 인프라라 혼잡 시간대에 500과 402를 간헐적으로 돌려줍니다. 그림 없는 일기가 생겼는데, 당시에는 사용자가 다시 시도할 길이 없었습니다. 감정 선택은 하루 한 번이라 생성 버튼도 다시 누를 수 없었습니다.

외부 혼잡은 서비스 쪽에서 막을 수 없습니다. 문제는 실패하면 사용자가 아무것도 할 수 없는 구조였습니다. 그래서 세 겹으로 대응했습니다.

1. 지수 백오프 재시도를 1회에서 4회로 늘렸습니다. 혼잡은 보통 몇 초 안에 풀립니다.
2. `POST /api/diary/{id}/image`를 추가했습니다. 일기 본문은 그대로 두고 삽화만 다시 만듭니다.
3. 그림 없는 일기 상세에 "다시 그려달라고 하기" 버튼을 두고, 감정 선택 뒤 실패하면 안내 모달로 다시 들어올 수 있게 했습니다.

외부 장애가 일기 저장을 막지 않는다는 [설계](03-architecture.md) 원칙이 화면까지 이어진 사례입니다.

## 회고

### 잘한 것

AI와 함께 만들었지만 순서는 백엔드 개발을 하던 때와 같았습니다. ERD와 API 경계, 피그마 화면을 먼저 정하고 프론트와 백엔드를 따로 작업했습니다. 그래서 AI에게 맡기는 일의 범위를 한 층으로 한정할 수 있었고, 생성된 코드가 설계를 벗어나는지 판단할 기준이 있었습니다.

제약을 설계로 풀었습니다. 운영비 0원 때문에 설계로 풀어야 하는 문제가 많았습니다. 휘발성 디스크는 URL 보존으로, Redis 부재는 fail-open과 폴백으로, 절전 DB는 커넥션 수명 조정으로 풀었습니다. 제약이 없었다면 돈으로 해결하고 지나갔을 문제들입니다.

프롬프트를 코드처럼 다뤘습니다. base와 extension 파일로 나눠 둔 덕분에 사례 1을 파일 단위로 진단하고 줄이고 검증할 수 있었습니다. 인스트럭션 길이를 로그에 상시 남겨 둔 것도 진단을 빠르게 했습니다.

실패 경로도 화면으로 봤습니다. 무료 외부 API는 반드시 실패한다는 전제로, 실패 지점마다 사용자가 할 수 있는 다음 행동을 두었습니다. 사례 4가 그 결과입니다.

### 다시 한다면

배포를 먼저 합니다. 토큰 만료와 URL 길이 초과처럼 로컬이 못 잡는 버그는 시간이 지나거나 환경이 달라야 드러납니다. 기능 80%가 아니라 로그인과 핵심 루프 하나가 도는 시점에 배포하고, 그 뒤 기능을 실서버에 얹으면 하나씩 일찍 만날 수 있습니다.

클라이언트와 서버의 계약을 테스트로 고정합니다. 401과 403의 구분은 알고 있었지만 서버 기본값을 확인하지 않고 프론트의 재발급 로직부터 만들었습니다. "만료 토큰은 401, 타인 리소스는 403" 같은 계약은 구현 초기에 통합 테스트로 묶어 둡니다.

밖에서 오는 데이터를 가정하지 않습니다. 로컬 파일 경로 기준으로 잡은 500자 컬럼이 외부 URL에 넘쳤고, 카카오 로그인 응답에서 블록 하나가 빠져 500이 났습니다. 가변 길이 컬럼은 처음부터 넉넉하게 잡고, 외부 API 응답은 전부 Optional로 파싱합니다.

알림을 먼저 겁니다. 문제가 생길 때마다 Render 로그를 직접 읽었습니다. 에러율과 응답 시간, 시스템 인스트럭션 길이에 경고를 걸어 두면 사용자 제보보다 먼저 알 수 있고, 품질 튜닝이 성능 저하로 번지는 것도 일찍 잡힙니다.

### 지금 상태

MVP까지 만들고 소수에게 열어 둔 상태이며, 함께하고 싶다는 사람이 생겨 정식 출시는 그 뒤로 미뤘습니다. 사용자가 거의 없어서 "고립 전 청년에게 일상 기록이 자리 잡을 수 있는가"라는 가설은 아직 검증하지 못했습니다. 지금까지 확인한 것은 인터뷰와 설계가 맞물린다는 것까지입니다. 출시 전에는 무료 티어로 버티던 인프라를 유료로 바꾸고, 예비 테스트용으로 넣은 "지금 미리 받아볼래요"를 뺍니다.
