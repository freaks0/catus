# 회고

> **요약** 잘한 것: 제약을 설계로 흡수했고, 프롬프트를 측정 가능하게 관리했고, 실패 경로를 UX로 간주했다. 아쉬운 것: 예외 번역의 안이함, 늦은 배포, 관측 수단 부재. 다시 한다면 로그인과 핵심 루프만 되는 시점에 먼저 배포한다.

## 잘했다고 생각하는 것

### 1. 제약을 설계로 흡수한 것

"운영비 0원"은 처음엔 족쇄였지만, 결과적으로 가장 많은 설계 경험을 만들어 줬다. 휘발성 디스크는 URL 보존 전략으로, Redis 부재는 fail-open과 폴백으로, 절전 DB는 커넥션 수명 튜닝으로 풀었다. 제약이 없었다면 돈으로 해결하고 지나갔을 문제들을 전부 설계로 풀었고, 그 과정이 이 포트폴리오에서 가장 이야기할 거리가 많은 부분이 됐다.

### 2. 프롬프트를 코드처럼 다룬 것

프롬프트를 리소스 파일로 모듈화(base와 extension 분리)한 초기 결정 덕분에, 품질 문제(이모티콘 남발)와 성능 문제(6.8초)가 왔을 때 파일 단위로 진단하고 압축하고 검증할 수 있었다. 인스트럭션 길이를 로그로 상시 노출한 것도 결정적이었다.

### 3. 실패 경로를 UX로 간주한 것

무료 외부 API는 반드시 실패한다는 전제로, 모든 실패 지점에 사용자가 할 수 있는 다음 행동을 설계했다(삽화 재생성 버튼, 안내 모달 재진입, 폴백 체인). 행복 경로만 만들던 습관에서 벗어난 계기였다.

### 4. 배포를 끝이 아니라 테스트의 시작으로 본 것

배포 직후 실사용에서 로컬이 못 잡는 버그 3개가 연달아 나왔다(토큰 만료 세션 사망, URL 길이 초과, 신규 카카오 콘솔 응답 변화). 전부 시간이 지나야, 환경이 달라야, 외부 서비스가 바뀌어야 드러나는 종류였다. 배포 후 며칠간의 실사용 검증을 일정에 포함해야 한다는 것을 체득했다.

## 아쉬운 것

### 1. 예외 번역의 안이함

`DataIntegrityViolationException`을 중복으로 번역한 코드는 "대부분 맞지만 가끔 거짓말하는" 코드였고, 실제로 오진단(길이 초과를 "이미 존재함"으로 표시)을 유발했다. 171개 테스트가 있었지만 이런 "예외 경로의 예외"는 커버하지 못했다. 테스트 커버리지 숫자보다 실패 경로의 분기를 의심하는 눈이 중요하다.

### 2. HTTP 시맨틱을 뒤늦게 맞춘 것

401(인증 실패)과 403(권한 없음)의 구분은 알고 있었지만, Spring Security 기본값이 403이라는 것을 확인하지 않고 프론트 재발급 로직을 먼저 만들었다. 클라이언트와 서버 간 자동화 로직의 계약에 해당하는 부분은 구현 초기에 양쪽을 맞춰 검증했어야 했다.

### 3. 스키마 여유분에 대한 상상력 부족

`image VARCHAR(500)`은 로컬 파일 경로 기준의 결정이었고, 저장 전략이 URL로 바뀌는 순간 깨졌다. 가변 길이 외부 데이터가 들어올 수 있는 컬럼은 처음부터 넉넉하게(혹은 TEXT로) 잡는 편이 변경 비용보다 싸다.

### 4. 관측 가능성(Observability) 부재

문제가 생길 때마다 Render 로그를 사람이 직접 읽었다. 에러율과 응답 시간에 대한 최소한의 알림(헬스체크 실패 알림은 UptimeRobot이 무료로 제공한다)이라도 초기에 걸어 뒀으면 사용자 제보보다 먼저 알 수 있었다.

## 다시 만든다면

1. 배포를 앞당긴다. 기능 80%가 아니라 로그인과 핵심 루프 1개가 도는 시점에 먼저 배포하고, 이후 기능을 실서버에 계속 얹는다. 환경 차이 버그를 조기에, 하나씩 만나는 쪽이 훨씬 싸다.
2. 외부 응답은 전부 Optional로 파싱한다. 외부 API DTO에 필수 필드를 가정하지 않는다.
3. 상태 코드 계약 테스트를 추가한다. "만료 토큰은 401", "타인 리소스는 403" 같은 계약을 통합 테스트로 고정한다.
4. 프롬프트에 길이 예산을 둔다. 시스템 인스트럭션이 n자를 넘으면 경고 로그를 남긴다. 품질 튜닝이 성능 저하로 번지는 것을 조기에 감지한다.

## 이 프로젝트로 말할 수 있게 된 것

- LLM 제품의 품질은 모델보다 프롬프트 운영 체계(모듈화, 측정, 회귀 검증)에서 갈린다는 것
- 무료 저사양 인프라의 제약 조건을 아키텍처 결정으로 바꾸는 과정
- 인증 토큰 수명 주기(발급, 만료, 재발급, 폐기)를 클라이언트와 서버 양쪽에서 끝까지 맞춰본 경험
- 행복 경로의 완성과 서비스의 완성 사이의 거리. 그 거리를 메우는 것이 실패 경로 설계, 예외 번역의 정직함, 배포 후 검증이라는 것
