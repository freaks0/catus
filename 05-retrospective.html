    회고¶

    요약 잘한 것: 제약에 설계로 대응했고, 프롬프트를 측정 가능하게 관리했고, 실패 경로를 UX로 간주했습니다. 아쉬운 것: 예외 번역의 안이함, 늦은 배포, 관측 수단 부재. 다시 한다면 로그인과 핵심 루프만 되는 시점에 먼저 배포합니다.

    잘했다고 생각하는 것¶

    1. 제약에 설계로 대응한 것¶

    운영비 0원 제약 때문에 설계로 풀어야 하는 문제가 많았습니다. 휘발성 디스크는 URL 보존 전략으로, Redis 부재는 fail-open과 폴백으로, 절전 DB는 커넥션 수명 튜닝으로 풀었습니다. 제약이 없었다면 돈으로 해결하고 지나갔을 문제들입니다.

    2. 프롬프트를 코드처럼 다룬 것¶

    프롬프트를 리소스 파일로 모듈화(base와 extension 분리)한 초기 결정 덕분에, 품질 문제(이모티콘 남발)와 성능 문제(6.8초)가 왔을 때 파일 단위로 진단하고 압축하고 검증할 수 있었습니다. 인스트럭션 길이를 로그로 상시 노출해 둔 덕에 진단이 빨랐습니다.

    3. 실패 경로를 UX로 간주한 것¶

    무료 외부 API는 반드시 실패한다는 전제로, 모든 실패 지점에 사용자가 할 수 있는 다음 행동을 설계했습니다(삽화 재생성 버튼, 안내 모달 재진입, 폴백 체인).

    아쉬운 것¶

    1. 예외 번역의 안이함¶

    DataIntegrityViolationException을 전부 중복으로 번역한 코드는 대부분 맞았지만 드문 경우에 틀렸고, 실제로 오진단(길이 초과를 "이미 존재함"으로 표시)을 유발했습니다. 171개 테스트가 있었지만 이런 예외 경로의 예외는 커버하지 못했습니다.

    2. HTTP 시맨틱을 뒤늦게 맞춘 것¶

    401(인증 실패)과 403(권한 없음)의 구분은 알고 있었지만, Spring Security 기본값이 403이라는 것을 확인하지 않고 프론트 재발급 로직을 먼저 만들었습니다. 클라이언트와 서버 간 자동화 로직의 계약에 해당하는 부분은 구현 초기에 양쪽을 맞춰 검증했어야 했습니다.

    3. 스키마 여유분에 대한 상상력 부족¶

    image VARCHAR(500)은 로컬 파일 경로 기준의 결정이었고, 저장 전략이 URL로 바뀌는 순간 깨졌습니다. 가변 길이 외부 데이터가 들어올 수 있는 컬럼은 처음부터 넉넉하게(혹은 TEXT로) 잡는 편이 변경 비용보다 쌉니다.

    4. 관측 가능성(Observability) 부재¶

    문제가 생길 때마다 Render 로그를 사람이 직접 읽었습니다. 에러율과 응답 시간에 대한 최소한의 알림(헬스체크 실패 알림은 UptimeRobot이 무료로 제공합니다)이라도 초기에 걸어 뒀으면 사용자 제보보다 먼저 알 수 있었습니다.

    다시 만든다면¶

    1. 배포를 앞당깁니다. 배포 직후 실사용에서 로컬이 못 잡는 버그 3개가 연달아 나왔습니다(토큰 만료 세션 사망, URL 길이 초과, 신규 카카오 콘솔 응답 변화). 전부 시간이 지나거나 환경이 다르거나 외부 서비스가 바뀌어야 드러나는 종류였습니다. 기능 80%가 아니라 로그인과 핵심 루프 1개가 도는 시점에 먼저 배포하고, 이후 기능을 실서버에 계속 얹으면 이런 버그를 하나씩 일찍 만날 수 있습니다.
    2. 외부 응답은 전부 Optional로 파싱합니다. 외부 API DTO에 필수 필드를 가정하지 않습니다.
    3. 상태 코드 계약 테스트를 추가합니다. "만료 토큰은 401", "타인 리소스는 403" 같은 계약을 통합 테스트로 고정합니다.
    4. 프롬프트에 길이 예산을 둡니다. 시스템 인스트럭션이 n자를 넘으면 경고 로그를 남깁니다. 품질 튜닝이 성능 저하로 번지는 것을 조기에 감지합니다.
