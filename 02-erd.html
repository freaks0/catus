    데이터 모델 (ERD)¶

    요약 9개 테이블. 핵심 결정은 넷입니다. 하루 1일기 유니크 제약을 동시성의 최종 방어선으로 삼았고, 조회 전용 테이블은 연관관계 대신 ID 컬럼을 썼고, 익명 응원은 일기가 삭제돼도 살아남도록 FK를 의도적으로 생략했고, 발신자 식별자는 암호화해 저장합니다.

    스키마 원본은 백엔드 저장소의 init-db.sql입니다. prod는 ddl-auto: validate라 이 스크립트가 유일한 스키마 생성 경로이며, 엔티티와 1:1로 동기화를 유지합니다.

    erDiagram
    users ||--o{ diaries : "하루 1개"
    users ||--o{ chat_logs : ""
    users ||--o{ weekly_letters : "주 1개"
    users ||--o| personality_state : "1:1"
    users ||--o{ analysis_history : "변화 이력"
    users ||--o| refresh_tokens : "1:1"
    users ||--o{ anonymous_messages : "수신자"
    diaries ||..o{ anonymous_messages : "FK 없음(의도)"

    users {
        bigint id PK
        varchar kakao_id UK
        varchar email UK
        varchar nickname
        time diary_time "일기 배달 시간"
        varchar today_emotion "오늘 선택한 감정"
        date today_emotion_date
        boolean diary_public "일기 공개 동의(기본 false)"
        boolean notification_anonymous
        boolean dark_mode
        boolean active "소프트 삭제"
        timestamp deleted_at
    }

    diaries {
        bigint id PK
        bigint user_id FK
        date diary_date "UK(user_id와 복합)"
        varchar content "2000"
        varchar image "1500, 로컬 경로 또는 외부 URL"
        varchar emotion
    }

    chat_logs {
        bigint id PK
        bigint user_id FK
        varchar user_message "1000"
        varchar ai_response "2000"
        timestamp created_at "IDX(user_id, created_at desc)"
    }

    weekly_letters {
        bigint id PK
        bigint user_id FK
        date week_start "UK(user_id와 복합), 월요일"
        varchar content "2000"
        boolean is_read
    }

    anonymous_messages {
        bigint id PK
        bigint diary_id "FK 미설정(의도)"
        varchar encrypted_sender_id "AES-256-GCM"
        bigint recipient_id FK
        varchar content "500"
        boolean is_read
    }

    personality_state {
        bigint id PK
        bigint user_id FK "UNIQUE"
        double openness "1~10, 중립 5.5"
        double conscientiousness
        double extraversion
        double agreeableness
        double neuroticism
        boolean initial_test_completed
        timestamp last_ema_update
    }

    analysis_history {
        bigint id PK
        bigint user_id FK
        double openness
        double conscientiousness
        double extraversion
        double agreeableness
        double neuroticism
        varchar update_type "INITIAL | EMA | MANUAL"
        timestamp recorded_at
    }

    refresh_tokens {
        bigint id PK
        bigint user_id UK
        varchar token "500"
        timestamp expiry_date
    }

    (이외에 스케줄러 분산 락용 shedlock 테이블이 있습니다. 도메인 데이터가 아니라 다이어그램에서 뺐습니다.)

    설계 결정과 이유¶

    (user_id, diary_date) 유니크 인덱스¶

    "하루에 일기 1개"는 애플리케이션에서 중복 체크를 하지만, 체크와 저장 사이의 경합(동시 요청, 스케줄러와 수동 생성 충돌)은 코드만으로 못 막습니다. 유니크 제약을 최종 방어선으로 두고, 서비스 코드는 DataIntegrityViolationException을 받아 중복 응답으로 번역합니다. 다만 무결성 위반이 전부 중복은 아니므로(컬럼 길이 초과 등) 재조회로 실제 중복 여부를 확인한 뒤 번역합니다.

    연관관계 대신 user_id Long 컬럼 (Diary, ChatLog, WeeklyLetter)¶

    JPA @ManyToOne 대신 ID 값만 보관했습니다.

    • 이 테이블들은 항상 user_id로 "내 것만" 조회하며, User 객체 그래프 탐색이 필요한 유스케이스가 없습니다.
    • 연관관계가 없으면 N+1, LazyInitialization, 양방향 순환 같은 문제 자체가 생기지 않습니다.
    • DB 레벨 FK 제약은 유지해 정합성은 지킵니다. 참조 무결성과 객체 참조는 별개 문제입니다.

    반면 PersonalityState와 AnalysisHistory는 분석 파이프라인에서 User 정보와 함께 다뤄져 @ManyToOne(LAZY)를 사용했습니다. 일괄 원칙보다 유스케이스 기준으로 골랐습니다.

    anonymous_messages.diary_id에 FK를 걸지 않은 이유¶

    일기를 삭제해도 받은 응원 메시지는 보존되는 것이 기획 의도입니다. 응원은 수신자의 자산이기 때문입니다. FK에 CASCADE를 걸면 함께 삭제되고, RESTRICT를 걸면 일기 삭제가 막힙니다. 그래서 FK를 생략하고 인덱스만 유지했으며, 이 결정은 스키마 주석으로 남겼습니다.

    발신자 암호화 (encrypted_sender_id)¶

    익명 응원의 "익명"을 DB 유출 상황에서도 지키기 위해 발신자 식별자를 AES-256-GCM으로 암호화해 저장합니다. 평문 컬럼이었다면 DB를 읽을 수 있는 누구나 익명성을 깰 수 있습니다. 신고 처리처럼 운영상 필요할 때만 서버 키로 복호화합니다.

    weekly_letters (user_id, week_start) 유니크: 자연키 기반 upsert¶

    주간 편지는 "주당 1통"이 자연키입니다. 유니크 제약 덕에 "이번 주 편지 미리 받기"를 여러 번 눌러도 upsert(있으면 내용 갱신과 미읽음 복귀)로 수렴하고, 스케줄러와 수동 생성이 충돌해도 중복이 생기지 않습니다.

    personality_state(현재) / analysis_history(이력) 분리¶

    현재 점수는 1:1 단일 로우로 빠르게 읽고, 변화 추적은 append-only 이력 테이블로 분리했습니다. 주간 편지의 "성향 변화 코멘트"는 이력의 최근 2건을 비교해 만듭니다.

    소프트 삭제 (users.active, deleted_at)¶

    탈퇴 시 하드 삭제 대신 비활성화합니다. 공개 일기 조회 등 모든 노출 쿼리가 active = true를 조건으로 겁니다.

    인덱스 전략¶

    인덱스 근거 쿼리
    diaries (user_id, diary_date) UNIQUE 오늘 일기 존재 확인, 월별 범위 조회, 중복 방어
    chat_logs (user_id, created_at DESC) "오늘 대화" 범위 조회, 최근 N건 컨텍스트 로드
    users (diary_time, active) 매시 정각 스케줄러의 대상 사용자 조회 (풀스캔 방지)
    anonymous_messages (recipient_id, is_read) 수신함과 미읽음 뱃지 카운트
    analysis_history (user_id, recorded_at) 기간별 성향 변화 그래프

    날짜 조회는 FUNCTION('MONTH', ...) 방식 대신 범위 조건(>= start AND < end)으로 작성해 인덱스를 타게 했습니다.
